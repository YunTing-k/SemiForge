## Principle Insights

### Physical Baseline Divergence Blocks Cross-Version Checkpoint Transfer
**Category**: Principle Insight
**Stage(s)**: fit-physical (primary), train-static (cross-impact)
**Symptom**: Attempting to mechanically splice IV KAN weights from a v90 checkpoint into a v92+ checkpoint produces degraded results (IV nonzero RMS degrades from ~0.10 to ~0.12 dex), even when the individual KAN weight tensors appear structurally compatible.
**Root Cause**: The fitted_params.json produced by fit-physical differs between runs (and across engine versions). These fitted physical parameters (Vth_t0, Vth_b0, nfac0, mu0, Cfr_*) serve as the "phase-1 baseline" for downstream KAN initialization — they determine input feature normalization centers/scales and the initial physical component of the model. When two checkpoints were built on different physical baselines, their KAN weights encode different residual corrections relative to different starting points. Simple tensor transfer ignores this dependency.
**Evidence**: Turn 8 (line 206) — direct checkpoint splicing: "v90 与当前 CV 的 phase-1 物理参数不同，简单替换张量会破坏共享物理核：IV 降到 0.12 dex，不能交付。" Turn 13 (line 434) — restoration: "用正确的 v90 base 物理目录复验后，精确 v90 IV 已恢复：residual scale=1.0，nonzero RMS 0.09992→0.09497，开态 0.04357，高电流 0.01842；先前异常是模型目录与 checkpoint 的物理基准不匹配。"
**Generalization**: Any time either the fit-physical engine changes (different oxide defaults, alignment logic, residual weights) or the input data changes, the resulting fitted_params.json parameters shift. Downstream PKAN checkpoints trained on one baseline cannot be ported to another without full re-initialization from the new physical kernel.
**Actionable Advice**: When Agent B adjusts fit-physical parameters and triggers a re-run, downstream stages (train-static, train-hysteresis) must be re-initialized from scratch — do not attempt to warm-start from a previous checkpoint. Conversely, if Agent C (train-static) falls back to fit-physical, the full static model must be retrained from the new baseline. Direct weight transplantation across physical baselines is systematically unsound.

**Additional Evidence from 05-22 session**: Turn 52, lines 1238-1243 — even with identical engine version and data, fitted_params.json values change between runs because: (a) data subsampling uses random seeds, (b) least_squares from different initial conditions converges to different local minima in the 34-parameter space, (c) fringe capacitances (Cfr_*) and trap parameters (Cit_t, Cit_b) interact strongly — small differences in one create compensatory changes in the other. The downstream KAN training script explicitly loaded fitted_params.json as frozen baseline (Turn 21, line 421: "复用你当前已经拟合好的物理核参数"), confirming the hard dependency.

### Fit-Physical Runtime Calibration
**Category**: Principle Insight
**Stage(s)**: fit-physical
**Symptom**: Agent B or the orchestrator may time out a fit-physical run thinking it is stalled, when in fact it is completing normally.
**Root Cause**: The physical kernel fitting runs entirely on CPU via scipy.optimize.least_squares with 6 sequential stages (plus CV shared trap fit). For a typical device dataset (~50K IV points, ~100K CV points at default max_nfev_scale=1.0), the total runtime is approximately 1 minute.
**Evidence**: Turn 27 (line 931) — fresh-start experiment: "先从原始 Excel 重新拟合物理核（约 1 分钟），再进行 140 epoch 的真实 base-PKAN 训练（约 1 分钟）。" The physical kernel completed in ~1 minute, while the downstream PKAN training began afterward. This timing was consistent across multiple fresh-start invocations throughout the session.
**Generalization**: On typical single-device datasets with default INI parameters, fit-physical is CPU-only and fast (~60s). It should not be the bottleneck in pipeline runtime. If the orchestrator reports a timeout during fit-physical, the problem is NOT that fit-physical is slow — it is either a data loading issue (e.g., malformed Excel files causing infinite parsing), or the timeout value was set too low relative to the data volume (larger max_iv_points / max_cv_points values scale linearly with residual vector size).
**Actionable Advice**: Agent B should NOT attempt to reduce max_nfev_scale or max_iv_points to "speed up" a fit-physical run that is already at defaults — the default runtime is ~1 minute and reducing parameters degrades quality with negligible speed gain. If the run exceeds ~5 minutes at defaults, suspect data issues (missing sheets, malformed columns, extremely large Excel files), not optimization budget. Use `inspect_xlsx` to verify data structure before adjusting parameters.

**Additional Evidence from 05-22 session**: Turn 12, lines 254-259 — the manual scipy least_squares fit (similar structure to the pipeline engine) also completed in ~1 minute for ~10K IV + 1200 CV points, even with the heavier qsolve computations. Turn 27, line 931 confirms the engine-level fit-physical takes ~1 minute, after which downstream KAN training (140 epochs on CUDA) consumes the remaining runtime in a minimal_run-style quick pipeline invocation.

### CV Residual Vector Can Dominate IV in Joint least_squares Optimization
**Category**: Principle Insight
**Stage(s)**: fit-physical (stages 4-5), train-static (joint CV+IV training)
**Symptom**: After the joint refinement stage (Stage 5) or during any multi-objective least_squares run that combines IV and CV residuals, the IV fit degrades — subthreshold slope flattens, nfac0 drifts to unrealistically high values, mu0 moves outside physically reasonable bounds. This manifests as acceptable total RMS (because CV residuals improved) but visibly worse IV curve shapes.
**Root Cause**: The combined residual vector concatenates IV and CV residuals. At default INI settings (max_iv_points=50000, max_cv_points=100000), CV points contribute up to 2× the number of residual terms that IV points do. The scipy.optimize.least_squares solver minimizes the sum across ALL residuals equally — it has no awareness that IV errors are log-space (decades) while CV errors are linear (farads). The optimizer will happily sacrifice 0.05 decades of IV accuracy to gain 0.1 pF of CV accuracy if that improves the total residual norm. Additionally, the CV-only stages (Stages 4 and 6) optimize fringe capacitances and trap parameters exclusively against CV data — if the optimizer over-fits these, the joint Stage 5 inherits parameters that are optimal for CV but suboptimal for IV.
**Evidence**: Turn 12, line 259 — the agent discovers: "正式跑完后，我看了图：现在的拟合被 CV 阶段和过宽的参数边界带偏了，nfac、mu0 和栅过驱饱和参数跑到不太物理的位置，导致 IDVBG 的亚阈值斜率太平。我要收紧几个物理边界，并让 CV 阶段只修正寄生电容，不再把核心 Cox 拉偏。" Turn 12, line 270 — the fix applied: "CV 不再拉动 IV 的核心 Cox，只用于寄生电容和一致性指标。" Turn 16, line 339 — user reinforces the constraint: "CV 里不能再有一个独立的 Vtrap_cgg 去替代 IV 的 Vth_t0/Vth_b0，也不能让 CV 单独拟合一套有效 Cox/阈值。"
**Generalization**: This applies whenever the residual vector combines IV and CV terms with disproportionate cardinality. The default max_cv_points=100000 vs max_iv_points=50000 (2:1 ratio) already risks CV dominance. If Agent B increases max_cv_points (e.g., to 200000) without proportionally increasing max_iv_points, the imbalance worsens. It also applies when cv_weight > 0 even in stages where IV is the primary target (cv_weight=0.22 in Stage 5 — a 22% CV contribution to the joint residual may still bias results).
**Actionable Advice**: When IV quality degrades after joint stages (fitted_params.json shows increasing iv_rms_log10_error_dec from Stage 3 to Stage 5, or Stage 4 is accepted but Stage 5 shows IV regression), Agent B should: (1) Reduce max_cv_points relative to max_iv_points (e.g., to 25000 vs 50000 = 1:2 ratio, reversing the default) to give IV more weight in the residual vector. (2) Check the fit_history: if Stage 4 (CV-only) was accepted with a large RMS improvement but Stage 5 (joint) shows IV degradation, the CV fringe parameters from Stage 4 may have pulled away from IV-optimal values — increase the reg_weight for Stage 4 to keep fringe caps closer to defaults. (3) If the issue persists, suspect that the physical kernel itself lacks sufficient IV expressivity (e.g., mobility degradation model too simple, channel length modulation insufficient) — the optimizer is compensating IV error through CV parameters because it has no better IV params to adjust. This is a model structure limitation, not a tuning issue.

### Off-State Measurement Floor Creates Systematic Subthreshold Fitting Error
**Category**: Principle Insight
**Stage(s)**: fit-physical, train-static (subthreshold metrics)
**Symptom**: The subthreshold RMS log-error (iv_subthreshold_rms_log10_error_dec) is high (>0.40) even when on-region and total IV fit is good. The fitted IV curve shows a smooth exponential decline through the off-region while the measured data flattens to a noise floor (~1e-12 A). The optimizer keeps trying to push the EKV channel current lower to match the exponential trend, but the measurement floor prevents convergence — resulting in perpetually high off-region error that inflates the total iv_rms_log10_error_dec.
**Root Cause**: The pure EKV channel current (`Ids = Ispec * (qs - qd)`) continues to drop exponentially as gate voltage decreases, but real measurements bottom out at the instrument's current resolution limit or device leakage floor. The log-space residual `log10(|Id_meas|) - log10(|Id_pred|)` explodes at the transition from subthreshold to deep-off when Id_pred drops below Id_meas (which is pinned to ~1e-12 A). The engine's Ioff0 and Gleak_ds parameters model this floor, but only when the external_ids() path is active (Rs0 + Rd0 > 10 Ω triggers the iterative solver, which applies leakage terms). When Rs0=Rd0=0 (default, below the 10 Ω threshold), the simpler direct Ids calculation is used and the leakage floor is NOT applied.
**Evidence**: Turn 12, line 264 — agent identifies the problem: "图里还有一个很清楚的问题：实测关态像仪器/漏电流地板，基本停在 1e-12 A 附近，而纯 EKV 通道电流会继续指数下降，所以关态和部分亚阈值误差被放大了。为了满足关态也基本拟合上，我会给拟合脚本加入一个很小的 D-S 漏电/测量地板项。" Turn 12, line 270 — the fix: "加入可拟合的 Ioff0/Gleak_ds 来描述关态漏电/仪器地板。" Turn 21, line 435 — in the PyTorch reimplementation, "qsolve 的极弱反型区域对自动微分太硬，第二轮就能把梯度带成 NaN" — confirming numerical instability in deep weak inversion.
**Generalization**: This affects any device where the off-state current hits the measurement system's noise/resolution floor. The EKV model's exponential off-state behavior is physically correct for an ideal device, but the measurement system adds a constant floor. The fitting engine already has Ioff0 and Gleak_ds to model this, but their effectiveness depends on whether the external_ids() path is triggered (Rs0 threshold = 10 Ω). Devices with negligible contact resistance (Rs0 ≈ 0) will bypass the leakage model. The issue is more severe when subthreshold weighting is high (default weight = 2.35 for |ID| in [-12.3, -8.7] range) because the optimizer is told to prioritize fitting a region where the model has limited expressivity.
**Actionable Advice**: Agent B should NOT increase max_nfev_scale to fix high subthreshold RMS — more iterations cannot overcome the measurement floor. Instead: (1) Check iv_subthreshold_rms_log10_error_dec vs iv_on_rms_log10_error_dec in fitted_params.json. If only the subthreshold metric is high (>0.5) while on-region is fine (<0.15), the floor is the issue. (2) Check if fitted Ioff0 is at its lower bound — if so, the optimizer is trying but the leakage model is inactive (Rs0 < 10 Ω). (3) Accept subthreshold error if it's solely from the deep-off floor region (-12.5 to -13.5 log|ID|). The quality threshold (0.35) was set with the total IV RMS in mind — a subthreshold-only contribution should not block progress if on-region fit is excellent. Use `accept_quality` with justification. (4) Consider setting iv_stage_alignment to "off" if alignment shifts are artificially bringing off-region points into the subthreshold weighting window.

### Contact Resistance Iteration Jitter → Recognition Only

**Diagnostic**: IV curves (especially IDVD) show sawtooth/zigzag oscillations in strong conduction region. Smooth intrinsic current, jagged external Ids.

**Agent Impact**: **None.** Agent B cannot change Rs0/Rd0 via `adjust_params` (these are EKV model parameters fitted by scipy, not INI-tunable). The 10Ω threshold, 30-step iteration, and 0.55/0.45 relaxation are engine-hardcoded.

**Correct Actions**: If you see IV jitter → check `fitted_params.json`. If Rs0 or Rd0 > 10Ω, the iterative solver is active and unstable. Options: (1) `accept_quality` if jitter is small and on-region RMS is acceptable, (2) `fallback_to_previous` (→ check-data) — the data may contain measurement artifacts that cause the optimizer to push Rs/Rd to unstable values. Do NOT increase `max_nfev_scale` — more iterations worsen the jitter.

**Evidence**: TURN 12: optimizer pushed Rd0 large, 30-step solver oscillated → produced sawtooth IV. Fix was to stop fitting Rs/Rd and use Ioff0/Gleak_ds for off-state leakage instead. IV RMS dropped from ~1 dec to 0.24 dec.

### Gate Saturation (Vmodsat/Vknee) IV-CV Conflict → Recognition Only

**Diagnostic**: IV saturation improves but CV develops artificial peaks+decline in strong inversion instead of rising to plateau. Vmodsat values in `fitted_params.json` are at non-default low values.

**Agent Impact**: **None.** Vmodsat/Vknee are fitted by scipy, not INI-tunable. The fundamental IV-CV tradeoff is structural — both share the same `one_sided_sat()` function.

**Correct Actions**: If both IV saturation and CV shape are poor → `fallback_to_previous` (data/model mismatch). If only CV shape is compromised but IV is acceptable → `accept_quality` — downstream KAN can learn saturation pattern as a VDS-dependent correction. Do NOT attempt to override Vmodsat values via INI adjustments (no INI key exists for these).

**Evidence**: TURN 12: optimizer pushed Vmodsat_t to lower bound → CV developed spurious peaks. Fix was to freeze Vmodsat at large defaults and let mobility/CLM handle saturation.

## Tuning Patterns

### When to Reduce max_cv_points (Not Increase max_nfev_scale) for IV Quality
**Category**: Tuning Pattern
**Stage(s)**: fit-physical
**Symptom**: IV RMS log error is above threshold (0.35), the on-region or transfer slope looks systematically wrong, but CV fit appears acceptable. The natural impulse is to increase max_nfev_scale for more optimization budget — but this is often wrong.
**Root Cause**: As described in "CV Residual Vector Can Dominate IV" above, the default 2:1 CV:IV point ratio biases the optimizer. Increasing max_nfev_scale gives the optimizer more iterations to further sacrifice IV accuracy for CV accuracy — making the problem worse, not better.
**Evidence**: Turn 12, lines 259-270 — multiple iterations where CV-bias ruined IV until the fitting strategy was restructured to decouple CV from core IV parameters. Turn 32, line 688 — even after extensive tuning: "CV RMS 从上一版 0.2282 降到 0.2171 dec，IV 非零 VDS RMS 也从 0.1208 降到 0.1082 dec" — which shows that CV optimization does NOT automatically help IV despite higher point counts.
**Actionable Advice**: If iv_rms_log10_error_dec is high and fit_history shows Stage 4 (CV-only) was accepted but Stage 5 (joint) has higher IV RMS than Stage 3 (output curves), try reducing max_cv_points to 25000 (1:2 ratio with default max_iv_points of 50000). This reduces CV's dominance in the joint residual vector. If this helps, the root cause is CV residual dominance. If it doesn't help, the IV expressivity itself is the bottleneck — this is a model structure limitation that max_nfev_scale cannot fix.

### When NOT to Increase max_nfev_scale
**Category**: Tuning Pattern
**Stage(s)**: fit-physical
**Symptom**: A specific error metric is high, and the natural response is to give the optimizer more iterations.
**Criteria to NOT increase max_nfev_scale**:
1. **Off-region RMS is high but on-region is good**: More iterations push the EKV model deeper into the noise floor with no improvement (see "Off-State Measurement Floor" above).
2. **CV shows sharp isolated spikes at high bias**: These may be numerical artifacts from the charge derivative computation or trap model instability — check `fit_history` for stage 6 rejection and inspect `cv_shared_trap_params.json` for extreme Cit or alpha values.
3. **IV jitter/sawtooth in IDVD**: These are Rs/Rd solver oscillation artifacts that worsen with more iterations (see "Contact Resistance" above).
4. **All fit_history stages show `accepted: true` and `status: 2` (converged)**: The optimizer already converged — more iterations won't help. The problem is data quality or model structure.
5. **nfeav used < max_nfev for all stages**: The optimizer didn't hit the iteration limit — it stopped because it converged (gradient below tolerance).
**Evidence**: Turn 12, lines 254-277 — four distinct quality problems (CV bias, off-state floor, Rs/Rd jitter, Vmodsat conflict), none of which were solved by increasing optimization budget. All required structural fixes to the fitting strategy.
**Actionable Advice**: Before adjusting max_nfev_scale, check fit_history: if all stages show `accepted: true`, the optimizer converged successfully and the problem is elsewhere. Check per-region IV metrics: if only one region is bad (e.g., subthreshold), the problem is likely model expressivity or data, not convergence.

### CV Data Quality Pre-Flight Check Before Tuning
**Category**: Tuning Pattern
**Stage(s)**: fit-physical
**Symptom**: CV fit quality is poor regardless of parameter tuning — CV RMS is high (>0.30 decades) and doesn't improve with increased max_nfev_scale or adjusted max_cv_points.
**Root Cause**: Some CV measurement configurations produce data that is fundamentally incompatible with the gate-CV charge model. Specifically: VDS-sheet CV measurements (where TG and BG are tied and a DC bias is applied to the drain) produce transcapacitance curves (Cgd + Cds type) that the engine's gate-to-channel terminal charge model cannot represent. Including these curves in the training data forces the optimizer to find unphysical parameter compromises.
**Evidence**: Turn 58, lines 1378-1380 — user explicitly deprioritizes vds: "CV的部分，我希望你可以先主要把cgg拟合好，其次是cbg，ctg。vds可以不太考虑效果。" Turn 63, lines 1554-1557 — systematic data quality audit reveals: "cgg 和 cbg 原始数据本身很干净；ctg 有两条轻微问题，尤其 VBG=3V 有两个大跳点，VBG=0V 有少量非单调点；vds 三条都明显粗糙，负跳变和大跳变很多。也就是说，CV 的主要问题不是全部数据都坏，而是 vds 这组和当前 gate-CV charge kernel 不是同一种测量对象，强行一起训会拖累通用模型。" Turn 63, line 1574 — refined strategy: "vds 这类端口不匹配数据剔除，ctg/cbg/cgg 里有跳点的曲线降权而不是删除" produces better results than forcing all CV curves into the objective.
**Generalization**: This applies whenever CV data includes measurement configurations beyond simple gate-to-channel capacitance (Cgg, Cbg, Ctg): VDS-terminal transcapacitance, split-CV with floating terminals, or pulsed CV with different pulse conditions. The engine's terminal_charges() model is designed for quasi-static gate CV — it cannot represent drain-coupled transcapacitance without a full non-quasi-static (NQS) model or explicit transcapacitance matrix. Including incompatible CV data will degrade ALL CV metrics, not just the mismatched curves.
**Actionable Advice**: Agent B should: (1) Use `inspect_xlsx` on CV_train.xlsx to identify sheet types. VDS sheets (where VDS is a sweep variable) are transcapacitance measurements — they will always fit poorly with the current gate-CV model. (2) Check v92_phase1_cv_data_decisions.csv — the engine already applies automatic filtering (drops incomplete series, single steps >20% span). If VDS sheets were kept by the filter, they are still being included in the fitting objective. (3) If CV RMS is high but cgg/cbg/ctg individually have reasonable RMS, the problem is concentrated in vds — use `accept_quality` with documentation. (4) If CV RMS is high across ALL sheets, the problem is not data quality but model mismatch — the Cox ratio, Vth values, or trap model parameters are wrong. Check v92_phase1_cv_gate_orientation.json for potential auto-swap errors.

## Session Meta-Notes (05-22)

The 05-22 session was a manual model development session (not a pipeline run), where a user iteratively built and refined a custom EKV-level physical kernel + KAN correction model for a single DG IGZO TFT device. Key observations relevant to fit-physical stage behavior:

- **No pipeline fit-physical invocations**: The session used a custom `fit_training_ready_dg_tft.py` script (Turn 11) with its own scipy least_squares implementation, NOT the engine's `fit_physical_kernel.py`. However, the fitting methodology (EKV formalism, 6-stage sequential optimization, CV shared trap fit) mirrors the engine's approach, making the insights about optimizer behavior, CV/IV coupling, and numerical stability directly transferable.

- **Extensive CV model iteration (Turns 12-63)**: The session spent ~50 turns iterating on the CV charge model — starting from simple QS charge differentiation (Turn 12), progressing through empirical wrappers (Turn 14), shared trap models (Turn 16), charge-based terminal charges (Turn 34), partition fixes (Turn 46), interface-local traps (Turn 52), EKV-style charge cores (Turn 53), OFF-state participation factors (Turn 54), parasitic extraction from OFF region (Turn 56), Cgg-common parasitic separation (Turn 58), distributed CV charge (Turn 59), tail-state residual charge (Turns 70-76). This mirrors the challenges the engine's fit-physical would face if CV measurements include diverse configurations — the core physical model has limited CV expressivity.

- **IV remained relatively stable**: Throughout all CV model changes, the IV core (EKV transfer + output curves) remained largely unchanged — the initial fit (Turn 12, after fixing Rs/Rd jitter and off-state floor) produced IV RMS ~0.24 dec which was never fundamentally exceeded. This supports the existing Session Meta-Note from the 06-29 session that fit-physical IV is robust.

- **KAN correction effectiveness depends on physical kernel quality**: The KAN could only effectively correct residuals when the underlying physical kernel was "close enough" — when the CV kernel had structural gaps (Turn 40: "CV 当前不合格，主要是模型结构问题"), KAN compensated by introducing non-physical oscillations (Turn 46: "你的 v4.1 loss 更低，但诊断和图显示它用更大的 KAN/scale 把 CV 拟成了强烈振荡"). This validates that Agent B's parameter tuning at fit-physical stage is the foundation — if fit-physical produces an inaccurate physical baseline, downstream KAN cannot reliably recover.

- **Data quality dominates CV fit quality**: The systematic data audit (Turn 63) showed that vds data had pervasive quality issues (negative slopes, large jumps), while cgg/cbg/ctg were clean. Excluding vds from training (while still evaluating it) produced better cgg/cbg/ctg fits without sacrificing IV. This mirrors the engine's existing CV series selection logic (Step 5: drops VDS sheet) and validates that this filtering is correct and necessary.
